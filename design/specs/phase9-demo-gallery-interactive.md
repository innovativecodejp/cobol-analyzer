# Phase 9 仕様：デモ B（ギャラリー）／ C（静的インタラクティブ）

- 起票日: 2026-07-26
- 前提:
  - `phase8-sample-corpus.md`（§10 の接続先）。CardDemo を submodule 固定（pin `59cc6c2fd7ebd7ef7925cad552a01a4b8b6e4d5e`）し、`SampleRegistry` で名前解決。`app/cbl` は **CB\* 12 / CO\* 18 / CS\* 1 = 31/31** で確定（`../../implement/log/working/2026-07-25_04_phase8-corpus-fixed-respike.md`）。
  - `phase6-export.md`（依存グラフ・移行優先度ランキング・Markdown エクスポート）。
  - `phase3-visualization.md` / `phase4-navigation.md`（AST/CFG/DFG 可視化・双方向ナビ）。

## §1 目的・背景

Phase 8 でコーパスを固定・名前解決可能にした。本フェーズでは、この固定コーパス（CardDemo）を解析した結果を **事前計算（precompute）** し、**バックエンド不要で静的にホストできる公開デモ**を 2 系統作る。

- **デモ B（ギャラリー）**: 解析結果を Phase 6 エクスポート（注釈レポート／移行設計書）＋図として静的に書き出し、閲覧専用のギャラリーとして見せる。
- **デモ C（静的インタラクティブ）**: 既存フロント（Vite/D3）を、`src/api/*.ts` の API 境界だけ**静的 JSON 読み込みに差し替え**て、バックエンドなしでインタラクティブに動かす。

ホスティング先は **GitHub Pages**（ポートフォリオ公開が主目的）。B・C を同一サイトに配置する。

## §2 スコープ / 非スコープ

**スコープ**
- 固定コーパス（レジストリ `carddemo`）を解析する**事前計算パイプライン**（ビルド時ステップ／ツール）。
- デモ B: ギャラリー静的書き出し（対象プログラムの注釈レポート＋図、プロジェクト移行設計書、全31本のランキング表）。
- デモ C: フロント API 境界の静的ローダ差し替えと、静的データモードでの `vite build`。
- GitHub Pages 用の出力レイアウト・`base` パス・帰属（Apache-2.0 / pin）表示。

**非スコープ（別フェーズ）**
- **ライブ・バックエンドのデプロイ**（任意 COBOL のアップロード再解析）。静的デモでは行わない（§10）。
- CardDemo 以外のコーパス追加（レジストリは拡張可能だが本フェーズは carddemo のみ）。
- 動的 CALL 解析・COPY REPLACING 等、Phase 6/7 で非スコープ済みの項目。
- 静的モードでのコメント挿入／削除・任意ソースのエクスポート生成（バックエンド前提のため無効化。§6-3）。

## §3 デモ対象プログラムの選定（確定）

31 本すべてを**フル成果物（注釈レポート＋図）**で書き出すと出力量・生成時間が大きい。ギャラリー／SPA の**深い成果物は選定した部分集合**に絞り、全31本は**ランキング表**で網羅する。

- **選定基準（決定論的・再現可能）**:
  1. `ProjectAnalyzeResult.ranking.entries` の **MDI 上位 N 本**（既定 **N = 8**）。
  2. **バケット代表 各1本**（`CB*` / `CO*` / `CS*`）。上位 N に含まれなければ追加（`CS*` は1本のみのため必ず含む）。
  3. 1・2 の和集合（重複排除）を「デモ対象集合」とする。上限の目安 **≤ 11 本**。
- 選定は固定コーパス（pin `59cc6c2`）と固定 MDI 重み（`appsettings.json`）に対して**一意に定まる**こと。順序・本数を事前計算ログに記録する。
- **全31本のランキング表**（rank / program / MDI / strategy / fanIn/fanOut）はギャラリー索引に掲載し、網羅性を担保する（フル成果物は対象集合のみ）。

> N・上限は既定値。実装時に出力量を見て調整する場合は事前計算ログに理由を残す（silent な打ち切りにしない）。

## §4 事前計算パイプライン（precompute）

固定コーパスを一度解析し、静的サイトが読む成果物を生成するビルド時ステップを設ける（`tools/` に新規ツール、または `CardDemoSpike` 拡張）。

- **入力**: `SampleRegistry` の `carddemo`（cobolDir=`app/cbl`、copybookDirs=`app/cpy` を `CobolPreprocessorOptions.CopybookPaths` へ）。
- **処理**:
  - **プロジェクト解析**（全31本）: `ProjectAnalyzer` 相当で `ProgramDependencyGraph` ＋ `ranking`（移行戦略付き）を算出。
  - **プログラム解析**（デモ対象集合のみ）: 各プログラムの `AnalyzeResult`（AST / CFG / DFG / Metrics）。
  - **Markdown エクスポート**: 対象集合の注釈レポート（`/api/export/annotation-report` 相当）＋プロジェクト移行設計書（`/api/export/migration-design` 相当）。
- **出力（JSON / Markdown / 図）**: §5・§6・§7 の配置に書き出す。JSON は既存型（`AnalyzeResult` / `ProjectAnalyzeResult` / `projectTypes.ts`）と**同一スキーマ**（フロントが無改造で読める）。
- **決定論**: pin 済み submodule ＋ 固定重みで出力が安定すること。生成物はコミットするか、ビルドで再生成するかを §7 で定める。

## §5 デモ B（ギャラリー）

閲覧専用（非インタラクティブ）の静的コレクション。

- **索引ページ**: プロジェクト概要 — 全31本の**移行優先度ランキング表**（strategy 付き）、**プログラム間依存グラフ図**、コーパス出所（sourceUrl / pin / Apache-2.0 帰属）。
- **各対象プログラム（§3 の集合）**:
  - 注釈レポート（Markdown → HTML）: MDI サマリー・指標内訳（CC/GD/AD/ND/RD/CS）・高リスクパターン・移行戦略提案。
  - 図: **AST / CFG / DFG**（Phase 3 の描画を静的画像＝SVG 推奨で書き出し）。
  - MDI スコア・リスクランクのサマリー。
- **プロジェクト移行設計書**（Markdown → HTML）を1本掲載。
- **形式**: Markdown ＋ 静的画像。Pages 配信のため HTML へレンダリングする（生成方法は実装裁量。既存 Markdown を素直に HTML 化）。

## §6 デモ C（静的インタラクティブ）

既存フロント（`implement/src/frontend`, Vite/D3）を**バックエンドなし**で動かす。

1. **API 境界の差し替え**: `src/api/analyzeApi.ts` / `projectApi.ts` / `exportApi.ts` / `commentApi.ts` は現在いずれも `fetch(${API_BASE}/api/...)` の薄いラッパ。**静的データモード**では、これらを事前計算 JSON をプログラム名でキーに読む**静的ローダ**へ切り替える（環境フラグ 例 `VITE_STATIC_DATA=1` で分岐、`API_BASE` へは一切アクセスしない）。UI/描画コンポーネントは無改造。
2. **維持する対話機能**: AST 折りたたみ、CFG/DFG ナビ、**ノード↔ソース双方向ハイライト（Phase 4）**、GO TO / PERFORM ジャンプ、データ項目の影響閉包、MDI パネル。プログラム選択は**デモ対象集合**（§3）から選ぶピッカー。
3. **静的モードで無効化 / 差し替え**:
   - **コメント挿入／削除**（ソースを書き換えて再解析＝バックエンド前提）: 静的モードでは**非表示 or 無効化**（明示）。
   - **エクスポート**（任意ソースの生成）: 静的モードでは**事前計算済み Markdown のダウンロード**に差し替え（`downloadAsFile` は静的資産を読んで保存）。任意ソースの再生成は不可。
4. **ビルド**: `vite build` を静的データモードで実行し、Pages 出力先へ生成。GitHub Pages プロジェクトサイト（`/<repo>/` 配下配信）に合わせ Vite の **`base` を設定**する。

## §7 ホスティング（GitHub Pages）

- **配信元**: `main` ブランチの **`docs/`** を Pages ソースにする（gh-pages ブランチ運用も可だが、`docs/` を既定とする）。
- **サイト構成（例）**:
  - `/docs/index.html` — ランディング（デモ B ギャラリーと C アプリへの導線、プロジェクト説明）。
  - `/docs/gallery/` — デモ B（索引 ＋ 各対象プログラム ＋ 移行設計書 ＋ 図）。
  - `/docs/app/` — デモ C（`vite build` 出力）。
  - `/docs/data/` — 事前計算 JSON（C が読む）／エクスポート Markdown（B・C が読む）。
- **`base` パス**: プロジェクトサイトはサブパス配信のため、Vite `base` と B の相対リンクを `/<repo>/` 前提で解決する。
- **帰属・ライセンス**: CardDemo の **Apache-2.0** 帰属（`NOTICE` 相当）と **pin コミット**をサイト上に明示（B の索引・C のフッタ等）。
- **生成物の扱い**: `docs/` 配下の成果物をコミットする（Pages が静的配信できる状態）。再生成手順（precompute → build → docs 反映）を実装ログに残す。

## §8 受け入れ基準

1. **事前計算の再現性**: 固定コーパス（pin `59cc6c2`）＋固定重みで precompute が決定論的に走り、**デモ対象集合が §3 の規則どおり一意**に定まる（ランキング順・本数をログに記録）。
2. **デモ B**: バックエンドなしで、索引（全31本ランキング表＋依存グラフ図）と対象 N 本のプログラムページ（注釈レポート＋AST/CFG/DFG 図）が静的に表示できる。
3. **デモ C**: `VITE_STATIC_DATA` で静的ビルドが通り、事前計算 JSON を読んで**インタラクティブ機能が backend への通信なし**で動く（`API_BASE` へアクセスしない）。プログラムピッカーがデモ対象集合を列挙。
4. **ホスティング**: `docs/`（または gh-pages）へ出力され、`base` サブパスで正しく解決。クリーンチェックアウトを静的配信して両デモが開ける。
5. **帰属**: Apache-2.0 帰属と pin がサイト上に表示される。
6. **既存資産非破壊**: 既存 `dotnet build` / `dotnet test`（現状 100 pass）とフロント既存テストがグリーン。precompute・静的モードは**追加**であり、ライブ API 経路（`API_BASE` 実 fetch）を壊さない。

## §9 テスト

- **precompute ツール**: 固定コーパスに対する出力の決定論を検証（ランキング順・本数・対象集合キーのスナップショット）。CardDemo 全走査はツール実行で担保し、ユニットに全解析は含めない（Phase 8 方針踏襲）。
- **静的ローダ（フロント）**: プログラム名で JSON 解決、未存在キーで明示エラー、`API_BASE` 非アクセス（静的モードで fetch を呼ばない）。
- **スモーク**: 生成した静的サイトを配信し、リンク解決・バックエンド未通信・両デモ起動を確認。

## §10 既知の制約・運用

- **ライブ再解析なし**: 静的デモは事前計算集合のみ。任意 COBOL のアップロード解析はバックエンド前提で本フェーズ非スコープ（別途「ライブ・デプロイ」フェーズで検討）。
- 静的モードではコメント挿入／削除・任意ソースのエクスポート生成は不可（§6-3）。
- **pin 更新時**は precompute → build → `docs/` 反映を再実行して成果物を更新する（コーパスは Phase 8 の pin 更新方針に従う）。
- 出力量（図・JSON）はデモ対象集合に比例。N 増加時はサイズに注意。
